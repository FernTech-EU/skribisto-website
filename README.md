# www.skribisto.eu

The Skribisto website: a static site built with [Zola](https://www.getzola.org),
in English and French, replacing the WordPress installation that still described
Skribisto 2.

The user manual and the FAQ are **not** here — they live in
[skribisto-help-website](https://github.com/jacquetc/skribisto-help-website) and
are served from `manual.skribisto.eu`.

## Build it

```bash
zola serve      # http://127.0.0.1:1111, live reload
zola build      # writes public/
zola check      # validates every internal and external link
```

Zola is a single binary: `cargo install zola`, your package manager, or a
[release tarball](https://github.com/getzola/zola/releases). CI pins 0.23.4.

## The one rule

**Nothing about a release is written by hand.** `data/release.toml` and
`data/news.toml` are generated by `scripts/sync_release_data.py` from two sources
of truth:

- the GitHub releases API — what is actually published, with the assets actually
  attached and their checksums;
- `NEWS.yml` in the application repository, with every entry marked `released`
  only when a matching published tag exists.

So the download page shows the packages that exist and no others, and a news
entry written ahead of its release renders as *not released yet* rather than as
shipped. The previous site advertised features the application did not have for
three years; this is the mechanism that stops that happening to a version number.

```bash
python3 scripts/sync_release_data.py --out data     # live
python3 -m unittest discover -s tests               # 17 tests, offline
```

A failed fetch is fatal and leaves the existing data files untouched: a stale
download page is a small problem, a blank or invented one is not.

`.github/workflows/sync-release.yml` runs it daily, on demand, and on a
`repository_dispatch` of type `release-published` — the header of that file has
the snippet to add to the application's release workflow so a release updates the
site immediately.

## Layout

```
config.toml         site config + every UI string, in both languages
content/            one .md per page, plus its .fr.md translation
data/               generated — do not edit
sass/main.scss      the whole stylesheet
static/img/         screenshots, icon, Open Graph card
templates/          base, index, page, download, news, 404
scripts/            the release-data sync
tests/              its tests
```

## Adding a language

1. Add `[languages.xx]` and `[languages.xx.translations]` to `config.toml`,
   translating every key in the `[translations]` block.
2. Copy each `content/*.md` to `content/*.xx.md` and translate it, front matter
   included.
3. `zola build`. Nothing else changes.

## Cutover checklist

- [ ] Push to `jacquetc/skribisto-website`, default branch `main`.
- [ ] Settings ▸ Pages ▸ Source: **GitHub Actions**.
- [ ] Custom domain `www.skribisto.eu` (`static/CNAME` already declares it), then
      wait for the certificate and tick *Enforce HTTPS*.
- [ ] DNS: `www` CNAME to `jacquetc.github.io`, apex A/AAAA to GitHub's Pages
      addresses (or an ALIAS to the same host) so `skribisto.eu` redirects.
- [ ] Export and archive the WordPress content **before** decommissioning it.
- [ ] Confirm the old URLs still resolve: `/index.php/download/`,
      `/index.php/donate/`, `/index.php/contribute/`, `/index.php/category/news/`
      are redirected by `aliases` in the front matter of the pages that replaced
      them. Anything else the old site had needs an alias adding.
- [ ] Leave `manual.skribisto.eu` alone — it is a separate deployment.
